Why this wave is different from Wave 6

Wave 6 picked single machines in Unknown and chaotic classes. It killed none of its 8 picks, and most of them turned out to be cryptid-like within a day.

Wave 7 changes three things.

  • Every pick is a table, not a machine. Each pick has 2 to 4 listed starts that share one mechanism. For most picks, the starts share the whole growing end of the tape. So one proof plus a short delta per extra start covers every line, as we did for #3 and its deltas #24/#25. After the critic, the five picks cover 15 list lines.
  • They are counters with mostly clean signals. Four picks are Skelet 1-like Class 1 tables outside K42. On the 75 and 175 tables, 4 skeletons cover the last 300 records at 1e9.
  • Critic correction. That record window is only about 1% of the run, so it says nothing about how events behave.
  • Critic correction. qsim does flag rules on these tables. On W7-1 and W7-4, every rule it proves is parity-flagged: a field is used up two at a time. Our kills #3, #11 and W5-5 show no rules at all at the same block sizes. The flag means the parity of each field when it runs out picks the next event. That is exactly what stage 1 checks, so it is a check, not a cryptid verdict.
  • The neighbouring class, Skelet 1-like Class 2, is our best class: 12 of 14 killed. W7-1's interior events look like #3's (critic check below).
  • Nobody on our side has looked at them. Waves 4 to 6 skipped the whole class as "mined". The last upstream proof file for the class is Sk1Machines.v (09-30, 5 machines from mxdys's numbered list). None of the picks has a table-level ledger row from before today, a claim or a machine folder.

The risk is shared, because the main picks are one class. K42, in this same class, turned out to be a cryptid family today. So the wave has a class kill switch: if two of W7-1, W7-2 and W7-4 end stage 1 on the cryptid stop, the third and W7-5 stop after their own stage 1, and we write a short class note instead of proofs.

Why each pick

W7-1 (4 lines). All four starts have the same growing end, and they differ in the oldest far-end blocks.

  • The tape is a list of (10^x 01^y) pairs separated by 00, plus a run of 1s at the growing end. Between events, every field only decreases. The rates roughly double toward the head (see the critic check).
  • Critic check. Two interior zero events are visible in the qsim trace, at about 1.3e9 and 1.7e9 steps (plan-data/critic/trace-75-pairs.txt). Both are the same uniform re-pairing: the dead field goes, and every pair to its right regroups one field over. That is #3's "re-pairing" move.
  • Critic correction. The far-end blocks are not frozen. They are the slowest budgets: 01^31 at 2e7 steps is 01^23 at 2.7e9. They differ by start, so each start meets its own far-end deaths, far beyond 1e12 steps.
  • The #24-style deltas are therefore cheap only if the core proof already handles a far-end death for any pair list.

W7-2 (2 lines). Both starts have the same growing end.

  • Today's 90-second qsim run (block 8) went to 10^2596 steps with 63 proved rules and no halt (plan-data/q175.jsonl).
  • Critic check (plan-data/critic/trace-175-rules.txt). Each step of the small far-end digit list doubles the big block: 863 → 1768 → 3545 → …, and 31808217 → 63616480 = 2·31808217 + 46. When the list runs out, the big block becomes the next digit list. This happened several times without a halt. No halving appears anywhere.
  • The 3 parity-flagged rules use up a left field two at a time. If that field always comes from a doubling, its parity is fixed. Stage 1 confirms this.
  • Critic correction. "Differ only in high-order digits" understates 489. At 1e9, its far-end digit list (0001^59 001 0010^364 0^5 0001^295 0^6 0001^3015) is longer than 175's (100^3 0100^98 1 0010^14). So the proof must be parametric over the whole far-end list, as planned.

How every Skelet pick runs

  1. Stage 1, go/no-go (2 h, Python, no Coq). - Fit the field system with rulefit, then build an exact accelerated simulator. Reuse the K42 one in reports/k42/ (5^k batches, translated-cycle detector). - Validate it against tools/sim to at least 1e10 steps, then run it far. - Classify every structural event. Both parity cases of every field death count as separate events, because the qsim flags say the parity picks the branch. The events are:
    • an interior field reaching 0 (W7-1: the re-pairing, seen twice so far);
    • a carry or transfer (W7-2: confirm every map is x → 2x + c);
    • a pair or field being born at the growing end;
    • a far-end death. Build these by hand where the natural run is too short: W7-1's far end dies only beyond about 1e12 steps.
    • Go if every event rule is affine in the fields, with at most a finite case table after a finite transient, and the halting transition is provably unreachable.
    • HALT route if the simulator reaches the halt: a checked-runner kill, as for C2-552 and W5-5.
    • Stop with the cryptid protocol if events branch on residues of growing numbers, or if the far end behaves like K42's glued escapes. Write the rules, flag the table, and stop.
  2. Stage 2 (2 h). Write proof.md for the representative start, starting from the nearest kill (#3 for W7-1, Sk1CounterMixed for W7-2, #30/#7 for W7-4). Use Variables, not Hypotheses, because check_kill bans the keyword (Sk1CounterMixed itself uses Hypothesis wall/one).
  3. Stage 3 (formal work, at most 1 agent-day per table). Stop if the core lemma fails coqc twice on the same structural issue.
  4. Deltas (3 h each). Same table, other start: keep the parent rules and prove a new base segment, as in #24. Stop a delta that needs new rules.

Class kill switch. If two of W7-1, W7-2 and W7-4 stop at stage 1 on the cryptid stop, the third and W7-5 stop after stage 1, and we write one class note.
