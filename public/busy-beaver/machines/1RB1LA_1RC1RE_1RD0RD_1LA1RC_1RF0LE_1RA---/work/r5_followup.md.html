1. What was dumped

Why the direct run starts at loop 288M, not 286M

Loop 286M is at step 4,329,936,209,482,021. That is 6.11e13 steps before the overflow, so a 2e13-step run from there would never reach it. Loop 288M is 3.147e11 steps (about 21 min of C) before the overflow, and it is also a row of the old 24 h log.

Both dumps are written: - work/r5_pre_overflow.json: loop 288,000,000, step 4,390,707,259,988,964. State D, head moving R, backsymbol 111010101010. 100,660,080 explicit cells, head at index 25,165,236, 79,689,235 nonzeros. - The file holds every left and right [word, exponent] block in left-to-right order (12-cell words; the 0^inf ends are listed as exponent "inf"). - dh is a directed-head string with block words and exponents, for example 0^inf 011110111111 ... Cell frame. Index 0 is the first cell of the first finite left block, which is absolute cell -60 of the blank-start run. This was checked against tools/sim.py from blank at loops 20k, 100k and 200k. At loop 288M the 1^4 is still at index 1..4, i.e. absolute -59..-56, the left edge of the 1e10 direct run. Every position in the log uses this frame: absolute = rel - 60. Cells left of the old edge get negative indices.

It also checks state and direction. A "verify" line is written each time. - From loop 20k to 400k: 19/19 exact. - Tests that the check fails when it should: refs shifted by a prepended zero block still pass, and a corrupted cell (including one at a negative position) is reported. - A resume from a checkpoint reproduces the same log lines. - The halting path matches tools/sim.py on 0 <A 101: halt after 4 steps, F reading 1.

4. How to read the log

One JSON object per line, keyed by ev: - start: the configuration loaded and the run limits. - log, once every 1e10 steps: - step (absolute) and rel_step (from 4,390,707,259,988,964); - state, and dir (the last move); - head, lo and hi (the span is the explicit cells plus every visited cell), span, nonzeros; - first1/last1 (the outermost 1s), head_from_right; - left, the 300 leftmost cells of the span, and right, the 200 rightmost; - steps_per_s, and t (seconds since the start). - verify: ok, and the qsim loop and step it was checked at. ref_cell0_rel is where qsim's own cell 0 falls in our frame (0 before the overflow; it goes negative when qsim adds blocks on the left). first_mismatch_rel / nonzero_outside_ref_rel are null when the match is exact. - HALT: the exact step of the halting transition, counted as a step as in tools/sim.py, plus halt_from/halt_read. It is followed by a halt_config line, the same fields as log. - end: reason is max_steps or halt.

Quick looks:

cd "[local working file]"
python3 -B scripts/r5_post_view.py --cells 80 --every 10   # table: rel/1e10, state, head, lo, hi, span, nonzeros, ...
grep -n '"ev":"HALT"' r5_post.log; tail -c 2000 r5_post.log

What to look for: - lo going negative: the tape grows to the left, a new left-moving front. - Whether hi (the right edge) resumes its slow growth, which was about +4 cells per cycle in the old epoch. - Whether the left window settles into a repeating gadget pattern (a new epoch) or keeps changing. - nonzeros over time.
